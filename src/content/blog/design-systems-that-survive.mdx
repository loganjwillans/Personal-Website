Every design system opens with the same slide: a component grid, a type scale, and a promise to
expand after launch. Two quarters later the promise is a folder of Figma files nobody opens, and the
product is shipping three slightly different buttons.

I have seen this from both sides — as the designer who built the library and as the person quietly
working around it. The cause is rarely craft. It is what the system asks of the people who have to
use it under a deadline.

<Card title="A system is a maintenance schedule" label="The reframe" color="blue">

The launch is the easy part. What kills a library is the second use: the request that does not fit,
the deadline that makes copying faster than contributing, the engineer who finds the API confusing
and builds a wrapper instead.

So the useful question is not "does this button have the right states?" It is "what happens when
someone needs a button that does not exist yet?" If the answer is "they wait for the systems team",
the system loses. If it is "they extend it in a documented way", it survives.

</Card>

Three habits have made the biggest difference in the libraries I have worked on.

<LooseCard title="What actually helps" color="cream">

- **Ship the escape hatch with the component.** Every survivor has a documented way to be wrong on
  purpose — a variant, an override slot, a composition pattern. An unapproved workaround is worse
  than an approved one.
- **Write the rule you would defend.** "Use this for primary actions" is a wish. "One primary action
  per view, because two competing primaries halved completion in checkout tests" is a rule with a
  reason, and reasons survive reorganisations.
- **Count the workarounds.** How often does a raw `<button>` appear where a system button should?
  That number tells you more about health than the component count does.

</LooseCard>

<Callout label="The uncomfortable part" title="Sometimes the team is right" tone="yellow" foot="A library that is behind should be treated as behind.">

If a product surface needs a pattern the library does not have, the library is the thing that is
late. Treating every deviation as a discipline problem is how systems teams end up with beautiful
libraries and no users.

</Callout>

<Quote attribution="A review of our own library">

We had documented the intention and missed the function. The spec said the component was for
errors; every real use was an empty state.

</Quote>

The version I aim for now is a system that is the fastest path for most cases, documented and
extensible for the rest, and honest about which cases it does not serve yet. That is a lot less fun
to present than a component grid. It is also the version still there a year later.
