I write small generative programs most weeks. Most never leave my machine. Some are worth sharing,
which means they have to run in a browser and cannot stay in Processing's Java mode.

The obvious move is to write them in p5.js from the start. I have tried that. I keep going back to
Processing first.

<Card title="Why start in Processing" label="The editor" color="blue">

Processing's editor is a place to think, not a place to ship. There is no module system, no build
step, and no expectation that the sketch will be maintained. That constraint is the point: an idea
at 9pm can be moving by 9:10.

It also has a better debugging loop for visual work. `println` and a visible frame rate go a long
way. p5.js is the same API with a different runtime, but the surrounding context changes how I work:
once I am in a project folder with a bundler, I start thinking about structure, and the sketch stops
being a sketch.

</Card>

The port is mostly mechanical. The API overlap is close enough that most sketches take a few
minutes to move.

<LooseCard title="The differences that matter" color="cream">

- `size()` becomes `createCanvas()`, and it goes inside `setup()`.
- `colorMode(HSB)` works the same, but hex strings and `color()` behave slightly differently at the
  edges.
- Anything reading from the filesystem — fonts, images, CSV — needs a web path and a `loadFont` or
  `loadImage` callback.
- `noise()` is the same, but seed handling is not. Reset it explicitly before capturing a poster
  frame.

</LooseCard>

Here is the core loop of a flow field, unchanged between the two versions:

<CodeBlock
  title="flow-field.js"
  language="js"
  code={`function draw() {
  for (const p of particles) {
    const angle = noise(p.x * scale, p.y * scale, zoff) * TWO_PI * 2;
    p.prev.set(p.x, p.y);
    p.x += cos(angle) * p.speed;
    p.y += sin(angle) * p.speed;

    stroke(cyan, 14);
    line(p.prev.x, p.prev.y, p.x, p.y);

    if (p.offscreen()) p.reset();
  }
  zoff += 0.0008;
}`}
/>

That is it. The visual character comes from three numbers — noise scale, particle count, and trail
alpha — and they behave identically in both runtimes.

<Callout label="What does not port" title="Patience, mostly" tone="yellow" foot="A browser sketch has an audience.">

Anything tied to the desktop runtime — high frame rates on large canvases, native file dialogs,
quality video export — stays in Processing. A browser sketch also needs a play button, a pause, and
a way to stop eating battery on a laptop. That is a requirement the desktop editor never imposed.

</Callout>

<Quote>

The whole thing takes an evening for something small. That is the correct budget for a sketch.

</Quote>
